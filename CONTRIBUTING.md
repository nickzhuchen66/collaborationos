# Contributing to CollaborationOS

Thank you for helping improve CollaborationOS.

## Choose the right channel

- Use [Discussions](https://github.com/nickzhuchen66/collaborationos/discussions)
  for adoption questions, early design exploration, and open-ended ideas.
- Open an issue for a reproducible public defect, documentation gap, schema
  proposal, or fixture/conformance improvement.
- Open a pull request only when the change is bounded, synthetic, and ready for
  review.

## Contribution boundary

The stable public baseline is a manual/static governance framework. The
unreleased `main` branch also contains experimental, no-execution Skills and a
Decision-Only helper. Contributions may improve public documentation,
protocols, schemas, templates, synthetic fixtures, conformance matrices,
adoption guidance, Skills, and Workflows.

## Contribution lanes

Choose one primary lane and keep the pull request bounded:

| Lane | Typical files | Required evidence |
|---|---|---|
| Documentation | `README*`, `docs/`, `examples/` | links, claim boundary, synthetic example |
| Protocol/schema | `02_Protocols/`, `03_Schemas_and_Templates/` | schema/template parity and positive/stop/failure fixtures |
| Conformance | `05_Conformance/` | stable fixture ID, expected result, matrix row |
| Skill | `skills/` | Skill validation, public source binding, trigger/output boundary |
| Workflow/tooling | `workflows/`, `tools/`, `tests/` | effective entry test, no-execution assertions, failure-closed case |
| Community | `.github/`, contribution docs | bounded process impact |

Do not submit:

- host secrets, credentials, personal data, private paths, or proprietary
  evidence;
- real client or employer material without clear publication rights;
- an executable capability described as accepted merely because it runs;
- changes that grant AI final authority, implicit retry, self-acceptance, or
  automatic promotion;
- copied third-party text without compatible licensing and attribution.

## Before opening a pull request

1. Use synthetic examples.
2. Keep source, fact, interpretation, decision, execution, and acceptance
   separate.
3. Update the relevant protocol, schema, template, fixture, and matrix together
   when their contract changes.
4. Preserve failure and supersession lineage.
5. Parse every changed JSON file strictly.
6. Check local Markdown links.
7. Scan for secrets, absolute paths, and personal identifiers.
8. State the claim ceiling and any unreviewed surface.

Run the public checks:

```bash
python3 tools/cos_wave1.py verify-bindings --cos-root .
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p "test_*.py" -v
python3 scripts/verify_repository.py
```

Maintainers regenerate the package manifest after staging the intended files:

```bash
python3 scripts/update_package_manifest.py
python3 scripts/verify_repository.py
```

## Pull request expectations

A reviewable pull request should explain:

- the problem and affected public assets;
- whether it changes a protocol, schema, template, fixture, matrix, or only
  documentation;
- the human authority and host-data boundaries that remain unchanged;
- positive, legal-stop, and failure behavior when applicable;
- validation performed and any remaining uncertainty;
- whether `PACKAGE_MANIFEST.json` must be regenerated by a maintainer.

For a Skill or Workflow change, also explain:

- the exact trigger and non-trigger conditions;
- why the output has no implicit authority;
- which public protocol/schema/profile owns the expected behavior;
- how positive, failed-closed, and downstream-not-started behavior was tested.

Keep unrelated refactors out of the same pull request. Real host evidence must
never be used as a public test fixture.

## Licensing

Unless explicitly stated otherwise, an intentional contribution submitted for
inclusion is provided under the Apache License 2.0, consistent with the
repository license. Do not submit material you are not authorized to license.

## Review

A pull request is a proposal. Automated checks establish consistency, not
correctness or authority. Merge requires maintainer review and does not itself
authorize any adopter's business decision, execution, or production use.
