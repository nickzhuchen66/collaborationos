# CollaborationOS Public Roadmap

This roadmap communicates direction, not authority or a delivery promise.
Every capability must preserve explicit human authority, host ownership, failure
truth, independent acceptance, and the published claim ceiling.

## Shipped: v0.1.0 Manual/Static Baseline

- P01-P07 protocol system;
- A01-A09 strict schemas and human templates;
- 126 synthetic fixtures and four manual conformance matrices;
- Manual/Static Gate Pack;
- new-host adoption guide and templates;
- synthetic positive, legal-stop, and failure/takeover walkthrough;
- Apache-2.0 public release and community policies.

## Shipped: v0.2.0 Public Agent Toolkit

- four public experimental, Codex-compatible Skills;
- dependency-free Decision-Only Workflow helper;
- source-binding and repository verification;
- Skill and Workflow contribution lanes;
- GitHub Actions validation and structured contribution templates.

## Now: Public Usability

- improve repository navigation and bilingual onboarding;
- clarify architecture and adoption boundaries;
- improve public issue, discussion, and contribution paths;
- collect schema, documentation, fixture, and adoption feedback;
- keep package manifests and release notes independently inspectable.
- collect feedback on four public experimental Skills and the Decision-Only
  Workflow helper;
- keep public Toolkit behavior local, dependency-free, and no-execution.

## Next: Reusable Operator Assets

Wave 1 includes separately structured Skills and a Decision-Only Workflow
derived from the manual baseline. They must not silently gain execution,
access, acceptance, retry, promotion, or production authority.

Before any executable package is accepted, it should have:

- a frozen capability and permission boundary;
- synthetic positive, legal-stop, and failure cases;
- independent review of the effective entry point;
- explicit human decision and acceptance roles;
- no implicit retry or self-promotion;
- a separate release and claim statement.

## Later: Portability Evidence

Cross-host portability remains an open validation objective, not a current
claim. Any future validation must use de-identified evidence, preserve each
host's source of truth, and distinguish protocol applicability from automated
or production readiness.

## Explicitly Not on the v0.2.x Roadmap

- autonomous final decision authority;
- silent host access or payload ingestion;
- automatic acceptance, retry, promotion, or canonical write;
- a production runtime presented as validated by documentation alone;
- publication of internal governance, private host evidence, or historical
  failure scenes.

## How to Influence the Roadmap

Use [GitHub Discussions](https://github.com/nickzhuchen66/collaborationos/discussions)
for design exploration. Open a bounded issue when a proposal has a concrete
problem statement, affected public assets, expected claim boundary, and
synthetic acceptance criteria.
